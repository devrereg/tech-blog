> 마인드리퍼블릭에서 운영하는 서비스 **WENOA**의 **인플루언서 검색 ETL 파이프라인**을 직접 구축하고, 초기에 해시태그 기준으로 매칭하던 카테고리를 ETL 가공 단계에서 채널 임베딩과 카테고리 임베딩의 코사인 유사도 기반으로 바꾼 과정을 정리했다.

## 프로젝트 개요

- **회사 / 서비스**: 마인드리퍼블릭 / WENOA
- **프로젝트명**: 인플루언서 검색 ETL 파이프라인 구축 및 카테고리 매칭 개선
- **일정**: 2025.07 ~ 2025.09 (3개월, 카테고리 매칭 개선 2주)
- **역할**: WENOA 백엔드 1인 개발 — ETL 파이프라인 전체(수집·가공·임베딩·색인) 및 검색 API
- **기술 스택**
  - Backend: FastAPI (백그라운드 비동기 수집·가공·임베딩·색인) · Spring Boot 3 + Kotlin (검색 API)
  - AI: GPT-4o-mini · BAAI/bge-m3 (로컬 임베딩 모델)
  - Data: Elasticsearch · Web Crawling (Google 검색 -> Instagram · YouTube · TikTok)
  - Infra: AWS EC2, Local PC(Web Crawling)

**설계 기준**

- 일 1,000개 키워드 × 키워드당 최대 50채널(일 최대 5만 채널, 중복 제외 시 그 이하)을 처리할 수 있어야 함
- 채널과 콘텐츠의 태그뿐 아니라 채널 정보 + 콘텐츠 이미지 + 텍스트 모두를 카테고리 판단에 반영해야 함
- 기존 카테고리 검색 API와 사용 방식에 영향을 주지 않아야 함

## 아키텍처

![WENOA 인플루언서 카테고리 매칭 ETL 파이프라인 아키텍처 다이어그램](/assets/img/posts/mindrepublic-wenoa-influencer-search/wenoa_influencer_etl_pipeline.png)

*WENOA 인플루언서 카테고리 매칭 ETL 파이프라인 — 일 1,000개 키워드로 채널을 수집하고, 가공(Transform) 단계에서 채널 임베딩과 카테고리 임베딩의 코사인 유사도로 `categories`를 매칭한 뒤 Elasticsearch에 색인한다.*

전체 작업은 **① 수집(Extract) → ② 가공(Transform) → ③ 색인(Load)** 순으로 진행했고, 검색은 기존 카테고리 검색 API를 그대로 사용했다.

**1. 수집 (Extract)**

- 일 1,000개 키워드로 Google 검색 → SNS별 채널 ID 파싱 → 채널 상세정보 크롤링 → 원본 데이터 저장. 클라우드 IP 차단을 피하기 위해 크롤링은 Local PC에서 수행

**2. 가공 (Transform)**

- 여러 대의 가공 서버가 채널 단위로 LLM 요약 → 임베딩 생성 → 코사인 유사도 계산을 하나의 트랜잭션으로 처리해 `categories`를 매칭

**3. 색인 (Load)**

- 매칭된 `categories`와 채널 메타데이터를 Elasticsearch에 색인

## 문제

초기에는 채널 및 콘텐츠의 해시태그를 기준으로 카테고리를 매칭하도록 구현했다.

### 1. 태그와 무관한 콘텐츠로 인한 낮은 연관성

태그와 관련 없는 콘텐츠가 많아 카테고리 검색 결과에 연관성이 낮은 채널이 노출됐다.

### 2. 태그만으로는 채널의 실제 성격을 반영하지 못함

채널의 성격은 태그보다 **실제 올리는 콘텐츠(이미지·게시물)**에서 드러나서 태그 기반 매칭은 적합하지 않았다.

---

## 해결

### 1. 채널 임베딩과 카테고리 임베딩의 코사인 유사도로 매칭

검색 방식은 그대로 두고, **Elasticsearch에 색인하기 전 ETL 단계에서 카테고리 매칭 정확도를 높였다.** 채널 콘텐츠를 반영한 임베딩 벡터와 카테고리 임베딩 벡터의 코사인 유사도를 계산해, **14개 카테고리 중 유사도 0.8 이상인 카테고리를 최대 3개까지** 채널의 `categories` 필드에 매칭했다.

- 채널의 메타데이터와 인기 게시물의 이미지·텍스트를 GPT-4o-mini로 요약해 채널 대표 텍스트로 정규화
- 로컬 임베딩 모델(bge-m3)로 채널 벡터 생성 (이미지 정보가 반영된 텍스트를 임베딩)
- 사전에 임베딩해 둔 카테고리 벡터와 코사인 유사도를 계산해, **14개 카테고리 중 0.8 이상인 카테고리를 최대 3개까지** `categories` 필드에 매칭 (0.8은 검색 결과를 확인하며 조정한 값)

**검색 시점이 아닌 ETL 단계에서 매칭한 이유**: 카테고리를 색인 전에 매핑해 두면 기존 `categories` 필터 검색과 검색 API를 바꾸지 않고 그대로 쓸 수 있고, 검색 시점에 임베딩 연산을 추가하지 않아도 되기 때문이다.

### 2. GPT-4o-mini로 이미지·텍스트 요약 후 기존 임베딩 모델(bge-m3) 활용

**요약 후 임베딩한 이유**: bge-m3는 텍스트 임베딩 모델이라 이미지를 직접 처리할 수 없다. 모델을 바꾸면 성능 검증에 공수가 크게 늘어나기 때문에, 기존 bge-m3를 그대로 쓰면서 GPT-4o-mini로 이미지와 텍스트를 설명 텍스트로 요약해 콘텐츠의 특징까지 채널 벡터에 반영했다.

---

## 결과

- 해시태그 대신 텍스트 + 콘텐츠 이미지 기준으로 카테고리가 매칭되어 **카테고리 검색 결과의 연관성 개선**
- 일 최대 5만 채널 규모를 처리하는 파이프라인 구조는 유지한 채, 가공 단계의 매칭 로직만 교체하는 방식으로 적용
- 기존 검색 API 변경 없이 데이터 가공 과정 개선만으로 검색 품질 개선
- 샘플 검수와 직원 피드백으로 카테고리 검색 결과 개선을 확인

## 회고

파이프라인을 처음 구축할 때 LLM 요약과 임베딩을 하나의 트랜잭션 안에서 처리하도록 설계했다. 임베딩은 무겁고 오래 걸려 그동안 DB 커넥션을 계속 점유했다. 요약·임베딩은 트랜잭션 밖에서 먼저 수행하고 DB 쓰기만 짧은 트랜잭션으로 분리했다면, DB 부하를 더 안정적으로 운영할 수 있었을 것 같다.

기존 텍스트 기반 임베딩 모델(bge-m3)을 그대로 사용한 점도 아쉬웠다. 실제로 멀티모달 임베딩을 지원하는 모델을 테스트하고 적용했으면 더 좋았을 것 같다.
