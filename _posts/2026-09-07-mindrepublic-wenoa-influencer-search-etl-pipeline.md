## 프로젝트 개요

- **회사 / 서비스**: 마인드리퍼블릭 / WENOA
- **프로젝트명**: 인플루언서 카테고리 매칭 개선을 위한 ETL 파이프라인 구축
- **일정**: 2025.09 (2주)
- **역할**: 카테고리 매칭 로직 설계 · 개발 (LLM 요약, 임베딩, 유사도 기반 매칭)
- **기술 스택**
  - Backend: Spring Boot 3 (Kotlin)
  - AI: GPT-4o-mini · BAAI/bge-m3 (로컬 임베딩 모델)
  - Data: Elasticsearch · Web Crawling (Google 검색 -> Instagram · YouTube · TikTok)
  - Infra: AWS EC2, Local PC(Web Crawling)


---

## 문제

기존에는 채널 및 콘텐츠의 해시태그를 기준으로 카테고리를 매칭했다.

- 태그와 관련 없는 콘텐츠가 많아 **카테고리 검색 결과에 연관성이 낮은 채널이 노출**됐다.
- 채널의 성격은 태그보다 **실제 올리는 콘텐츠(이미지·게시물)**에서 드러나서 태그 기반 매칭은 적합하지 않았다.

---


## 해결

검색 방식은 그대로 두고, **Elasticsearch에 색인하기 전 ETL 단계에서 카테고리 매칭 정확도를 높임.** 채널 콘텐츠를 반영한 임베딩 벡터와 카테고리 임베딩 벡터의 코사인 유사도가 **0.8 이상인 카테고리만** 채널의 `categories` 필드에 매칭했다.


**설계 기준**

- 기존 파이프라인 규모(일 1,000개 키워드, 최대 5만 채널)를 그대로 처리할 수 있어야 함
- 채널과 콘텐츠의 태그뿐 아니라 채널 정보 + 콘텐츠 이미지 + 텍스트 모두를 카테고리 판단에 반영해야 함
- 기존 카테고리 검색 API와 사용 방식에 영향을 주지 않아야 함


## 아키텍처

![WENOA 인플루언서 카테고리 매칭 ETL 파이프라인 아키텍처 다이어그램](/assets/img/posts/mindrepublic-wenoa-influencer-search/wenoa_influencer_etl_pipeline.png)


- **수집 (Extract)**: 일 1,000개 키워드로 Google 검색 → SNS별 채널 ID 파싱 → 채널 상세정보 크롤링 → 원본 데이터 저장. 클라우드 IP 차단을 피하기 위해 크롤링은 Local PC에서 수행
- **가공 (Transform)**: 여러 대의 가공 서버가 채널 단위로 아래 과정을 하나의 트랜잭션으로 처리
  - 채널의 메타데이터와 인기 게시물의 이미지·텍스트를 GPT-4o-mini로 요약해 채널 대표 텍스트로 정규화
  - 로컬 임베딩 모델(bge-m3)로 채널 벡터 생성 (이미지 정보가 반영된 텍스트를 임베딩)
  - 사전에 임베딩해 둔 카테고리 벡터와 코사인 유사도를 계산해, **0.8 이상인 카테고리만** `categories` 필드에 매칭
- **색인 (Load)**: 매칭된 `categories`와 채널 메타데이터를 Elasticsearch에 색인
- **검색**: 기존 카테고리 검색 API가 개선된 `categories` 필드를 그대로 사용함

**검색 시점이 아닌 ETL 단계에서 매칭한 이유**: 카테고리를 색인 전에 매핑해 두면 Elasticsearch categories 필드의 필터 검색을 그대로 활용할 수 있어 검색이 빠르다. 검색 시점에 검색어를 임베딩하고 벡터 검색을 수행하면 응답 속도가 느려지기 때문

**요약 후 임베딩한 이유**: bge-m3는 텍스트 임베딩 모델이라 이미지를 직접 처리할 수 없다. 모델을 바꾸면 성능 검증에 공수가 크게 늘어나기 때문에, 기존 bge-m3를 그대로 쓰면서 GPT-4o-mini로 이미지와 텍스트를 설명 텍스트로 요약해 콘텐츠의 특징까지 채널 벡터에 반영했다.

---

## 결과

- 해시태그 대신 텍스트 + 콘텐츠 이미지 기준으로 카테고리가 매칭되어 **카테고리 검색 결과의 연관성 개선**
- 일 최대 5만 채널 규모의 기존 파이프라인에 매칭 로직만 교체하는 방식으로 적용
- 기존 검색 API 변경 없이 데이터 가공 과정 개선만으로 검색 품질 개선

---

## 회고
- 기존에 개발되어 있던 구조를 그대로 사용하다 보니 LLM 요약과 임베딩이 하나의 트랜잭션 안에서 처리되었다. 임베딩은 무겁고 오래 걸려 그동안 DB 커넥션을 계속 점유했다. 요약·임베딩은 트랜잭션 밖에서 먼저 수행하고 DB 쓰기만 짧은 트랜잭션으로 분리했다면, DB 부하를 더 안정적으로 운영할 수 있었을 것 같다.
- 기존 텍스트 기반 임베딩 모델(bge-m3)을 그대로 사용한 점이 아쉬웠다. 실제로 멀티모달 임베딩을 지원하는 모델을 테스트하고 적용했으면 좋았을 것 같다.
