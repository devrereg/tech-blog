> 라이프오아시스에서 운영하는 서비스 **MAUM**의 **Admin/백오피스 개발 및 자동화** 기록입니다. 내부 직원의 업무 효율을 높이기 위해 ① CS 대응 과정에서 20초 이상 걸리던 **800만 유저 대상 이름·이메일 검색**을 MySQL **Fulltext Index** 기반으로 다시 만들었고, ② 매월 개발자가 직접 코드로 세팅하던 **마케팅 프로모션**을 Admin 기능으로 옮겨 마케터가 개발자 개입 없이 운영하도록 만들었습니다.

## 프로젝트 개요

- **회사 / 서비스**: 라이프오아시스 / MAUM
- **프로젝트명**: Admin/백오피스 개발 및 자동화
- **일정**: 2023.05 ~ 2025.05 (2년)
- **기술 스택**: Kubernetes (K8s) · Spring Boot 3 (Kotlin) · MySQL

**설계 기준**

- 내부 직원 업무 효율화를 위한 기능 개발 및 성능 개선
- 반복 업무는 개발자 개입 없이 실무자(마케터·CS)가 직접 운영할 수 있는 구조로 전환

## 아키텍처

작업은 서로 다른 두 축으로 진행됐다. **① CS 대응 유저 검색 성능 개선**과 **② 매월 반복되는 마케팅 프로모션 세팅 자동화**다.

### 1. 유저 검색 성능 개선 — LIKE 스캔 → Fulltext Index

![MAUM Admin 유저 검색 성능 개선 아키텍처(2023.05~2025.05) 다이어그램. 기술 스택은 K8s, Spring Boot3 + Kotlin, MySQL. CS 담당자가 K8s Cluster 안의 Admin/백오피스 서버(Spring Boot3 + Kotlin)에 접속해 이름 또는 이메일로 유저를 조회하면, Admin 서버가 MySQL의 user 테이블(약 800만 행)에 질의한다. 개선 전(Before): WHERE name LIKE '%값%' OR email LIKE '%값%' 형태의 쿼리라 인덱스를 타지 못하고 풀 테이블 스캔이 발생해 응답에 20초 이상 소요됐다. 개선 후(After): name·email 컬럼에 ngram 파서 기반 Fulltext Index를 생성하고, SELECT ... WHERE MATCH(name, email) AGAINST('값' IN BOOLEAN MODE) 쿼리로 전환해 Fulltext 인덱스 탐색으로 200ms 내에 응답한다. 오른쪽에 결과로 '유저 검색 응답 20s -> 200ms, 약 100배 향상'이 표시된다](/assets/img/posts/maum-admin-automation/maum_admin_backoffice_architecture_1_user_search.drawio.png)

*MAUM 유저 검색 성능 개선 (2023.05~2025.05) — CS 담당자가 Admin 서버(Spring Boot 3 + Kotlin, K8s)를 통해 약 800만 행의 `user` 테이블을 이름·이메일로 조회한다. `LIKE '%값%'` 풀 테이블 스캔(20s+)을 `name`·`email`의 ngram Fulltext Index + `MATCH(name, email) AGAINST(... IN BOOLEAN MODE)` 쿼리(200ms)로 전환했다.*

- Admin의 유저 조회는 CS 담당자가 이름·이메일로 특정 유저를 찾는 화면이다. 대상 `user` 테이블은 약 **800만 행** 규모다.
- 기존에는 `WHERE name LIKE '%값%' OR email LIKE '%값%'` 형태라 인덱스를 타지 못하고 **풀 테이블 스캔**이 발생했다.
- `name`·`email`에 **ngram 기반 Fulltext Index**를 생성하고, 검색 쿼리를 `MATCH(name, email) AGAINST('값' IN BOOLEAN MODE)`로 전환했다.

### 2. 마케팅 프로모션 세팅 자동화 — 코드 세팅 → Admin 기능

![MAUM Admin 마케팅 프로모션 세팅 자동화 아키텍처(2023.05~2025.05) 다이어그램. 기술 스택은 K8s, Spring Boot3 + Kotlin, MySQL. 개선 전(Before): 매월 진행하는 마케팅 프로모션마다 개발자가 프로모션 기간·대상·보상·조건 로직을 직접 코드로 작성하고 배포하는 데 건당 2~3일이 소요됐다. 마케터는 프로모션을 바꾸려면 개발자 일정에 맞춰야 했다. 개선 후(After): Admin에 프로모션 관리 기능(생성/수정/관리)을 개발해, 마케터가 K8s Cluster 안의 Admin 서버(Spring Boot3 + Kotlin) 화면에서 프로모션 기간·대상·보상·조건을 입력하면 프로모션 설정이 MySQL에 저장된다. 서비스 API 서버가 런타임에 이 설정을 읽어 프로모션을 적용하므로, 프로모션 생성·수정·조기 종료에 개발자 배포가 필요 없다. 오른쪽에 결과로 '월 2~3일 개발 공수 절감', '마케터가 개발자 개입 없이 직접 운영, 마케팅팀 운영 자율성 확보'가 표시된다](/assets/img/posts/maum-admin-automation/maum_admin_backoffice_architecture_2_promotion_automation.drawio.png)

*MAUM 마케팅 프로모션 세팅 자동화 (2023.05~2025.05) — 매월 개발자가 코드로 작성·배포하던 프로모션(건당 2~3일)을 Admin의 프로모션 관리 기능(생성/수정/관리)으로 옮겼다. 마케터가 화면에서 정의한 프로모션 설정을 MySQL에 저장하고, 서비스 API 서버가 런타임에 읽어 적용하므로 프로모션 생성·수정·종료에 개발자 배포가 필요 없다.*

- 매월 진행하는 프로모션은 그동안 개발자가 **기간·대상·보상·조건을 코드에 직접 작성하고 배포**하는 방식이었다.
- Admin에 **프로모션 관리 기능(생성/수정/관리)**을 개발해, 마케터가 화면에서 프로모션을 정의하면 설정이 MySQL에 저장된다.
- 서비스 API 서버는 런타임에 이 설정을 읽어 프로모션을 적용한다. 프로모션 생성·수정·종료에 **개발자 배포가 필요 없어졌다**.

## 문제

### 1. 800만 유저 대상 LIKE 검색으로 인한 CS 대응 지연

CS 대응을 위해 이름·이메일로 유저를 조회하는 일은 **매우 빈번하게** 발생한다.

- 검색이 `name LIKE '%값%'`·`email LIKE '%값%'` 기반이라, 앞부분이 고정되지 않은 부분 문자열 검색에서는 **인덱스가 무력화**되고 800만 행을 전부 스캔했다.
- 유저 한 명을 찾는 데 **20초 이상** 걸렸고, 문의가 몰리는 시간대에는 CS 담당자가 조회 결과를 기다리느라 응대 자체가 밀렸다.
- 조회가 느리니 담당자들이 여러 번 재검색하게 되고, 그만큼 DB 부하도 가중됐다.

### 2. 매월 반복되는 마케팅 프로모션 세팅에 개발자 리소스 소모

- 매월 진행하는 마케팅 프로모션마다 개발자가 로직을 **직접 구현·배포**해야 했고, 건당 **2~3일**의 개발 공수가 들었다.
- 내용은 매번 조금씩 다르지만 구조는 비슷한 **반복 작업**이라, 개발 리소스가 정기적으로 여기에 묶였다.
- 마케터는 프로모션 기간·조건을 바꾸고 싶어도 개발자 일정에 맞춰야 했고, 급한 수정이나 조기 종료도 배포를 거쳐야 했다.

---

## 해결

### 1. Fulltext Index + MATCH AGAINST 기반 검색으로 전환

부분 문자열 `LIKE` 검색을 **Fulltext 검색**으로 교체해 인덱스를 타도록 만들었다.

- **ngram Fulltext Index 생성** — 한글 이름·이메일에 대응하기 위해 `name`·`email` 컬럼에 **ngram 파서 기반 Fulltext Index**를 추가했다.
- **쿼리 전환** — 검색 쿼리를 `MATCH(name, email) AGAINST(:keyword IN BOOLEAN MODE)`로 바꿔, 풀 테이블 스캔 대신 **Fulltext 인덱스 탐색**으로 후보를 좁히도록 했다.
- **동작 검증** — 개선 전후로 동일한 검색어에 대해 응답 시간과 결과 정확도를 비교해, CS가 쓰던 조회 패턴에서 결과 누락 없이 속도만 개선되는지 확인했다.

### 2. Admin 프로모션 관리 기능으로 운영 주체 이관

프로모션을 **코드가 아니라 데이터로** 다루도록 바꾸고, 그 데이터를 마케터가 직접 관리하게 했다.

- **프로모션 관리 화면 개발** — Admin에 프로모션 **생성 / 수정 / 관리** 기능을 만들어, 마케터가 기간·대상·보상·조건 등 프로모션 구성 요소를 화면에서 입력·변경할 수 있게 했다.
- **설정 기반 적용 구조** — 입력된 프로모션은 MySQL에 설정으로 저장되고, 서비스 API 서버가 런타임에 이 설정을 읽어 적용한다. 프로모션이 바뀌어도 **서버 배포가 필요 없다**.
- **운영 자율성 확보** — 프로모션 시작·수정·조기 종료를 마케터가 스스로 처리하게 되어, 개발자는 프로모션 개별 건에서 완전히 빠졌다.

## 결과

### 1. 800만 유저 대상 LIKE 검색으로 인한 CS 대응 지연

- 유저 검색 응답 속도가 **20초 → 200ms로 개선**됐다. (약 **100배** 향상)
- CS 담당자가 조회 결과를 기다리지 않고 바로 응대할 수 있게 되어, 문의 대응 시간이 단축됐다.

### 2. 매월 반복되는 마케팅 프로모션 세팅에 개발자 리소스 소모

- 매월 **2~3일씩 들던 프로모션 개발 공수가 절감**됐다.
- 마케터가 개발자 개입 없이 프로모션을 직접 생성·수정·운영하게 되어, **마케팅팀의 프로모션 운영 자율성**을 확보했다.
