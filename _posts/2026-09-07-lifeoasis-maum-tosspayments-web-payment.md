> 라이프오아시스에서 운영하는 서비스 **MAUM**의 **토스페이먼츠 웹결제 연동** 기록입니다. iOS 인앱결제 수수료가 30%로 인상되면서, 앱 내 재화 구매를 인앱결제 대신 **토스페이먼츠(TossPayments) 웹결제로 유도하는 결제 플로우**를 설계했습니다. 동시에 **결제는 성공했는데 재화가 지급되지 않는** 정합성 깨짐을 어떻게 감지하고 되돌리는지에 초점을 맞췄습니다.

## 프로젝트 개요

- **회사 / 서비스**: 라이프오아시스 / MAUM
- **프로젝트명**: 인앱결제 수수료 절감을 위한 토스페이먼츠 웹결제 연동
- **일정**: 2024.03 (1개월)
- **기술 스택**: Spring Boot 3 (Kotlin) · TossPayments API · MySQL · Kubernetes (K8s) · Slack

**설계 기준**

- TossPayments API와 내부 DB 간 데이터 정합성 확보를 위한 **보상 트랜잭션(Saga)** 설계
- iOS 인앱결제 수수료 인상에 대응해 **웹결제로 유도하는 결제 플로우** 구현

*MAUM 결제–재화 지급 정합성 흐름 (2024.03) — TossPayments 결제가 승인(success)되면 서버가 로컬 트랜잭션으로 결제 로그 기록과 재화 지급을 처리한다. 로그 기록/재화 지급이 모두 성공하면 사용자에게 완료 응답하고, 하나라도 실패하면 Saga 보상 트랜잭션으로 TossPayments 결제를 자동 환불한 뒤 실패 로그를 MySQL에 적재하고 Slack Bot으로 실시간 통지해 CS/개발팀이 대응한다.*

전체 흐름은 **① 결제 승인(TossPayments) → ② 재화 지급 로컬 트랜잭션 → (실패 시) ③ Saga 보상 트랜잭션** 순으로 이어진다. iOS 앱에서 인앱결제 대신 토스페이먼츠 웹결제로 유도하는 결제 플로우 위에서 동작한다.

**1. 결제 승인 — TossPayments**

- 사용자가 결제를 요청하면 K8s Pod 위의 API 서버(Spring Boot 3 + Kotlin)가 TossPayments API로 결제를 요청하고 **success 응답**을 받는다.
- 이 시점에 **실 결제는 완료**된 상태가 된다.

**2. 재화 지급 — 로컬 트랜잭션**

- success 수신 후, API 서버는 **로컬 트랜잭션**으로 MySQL에 결제 로그를 기록하고 유저에게 재화를 지급한다.
- 로그 기록과 재화 지급이 **모두 성공하면** 사용자에게 재화 지급 완료를 응답한다.

**3. 보상 트랜잭션 — 실패 시 자동 환불 + Slack 알림**

- 로그 기록 또는 재화 지급 단계에서 **예외가 발생하면(No)**, **Saga 보상 트랜잭션**을 실행해 직전에 성공한 TossPayments 결제를 **자동 환불(취소) API로 롤백**한다.
- 환불 완료 후 **결제 실패 로그를 MySQL에 적재**하고, **Slack Bot으로 실시간 알림**을 전송한다.
- Slack 알림을 받은 **CS/개발팀이 원인 파악 및 신속 대응**에 착수한다.

**K8s 구성**

- API 서버는 K8s 위에서 상시 운영하며, 결제 승인·재화 지급·보상 처리를 모두 한 서비스에서 담당한다.

## 문제

### 1. 결제는 성공했으나 재화가 지급되지 않는 정합성 이슈

TossPayments 웹결제 자체는 정상적으로 승인되지만, 그 **직후 서버 처리에서 문제가 생기는** 경우가 있었다.

- TossPayments 결제는 **성공**했는데, 내부 DB **결제 로그 기록**이나 **재화 지급** 과정에서 오류가 발생하면, 실 결제는 완료됐음에도 **유저에게 재화가 지급되지 않는** 상태가 만들어진다.
- 외부 PG(결제 완료)와 내부 DB(재화 미지급)의 상태가 어긋나는데, 이를 **자동으로 감지하거나 되돌릴 장치가 없었다**.
- 고객은 "결제했는데 재화가 없다"고 문의하고, 운영자는 어떤 결제가 실패했는지 로그를 일일이 뒤져야 하는 구조였다.

### 2. iOS 인앱결제 수수료 30% 인상으로 인한 수익성 저하

- iOS 인앱결제(IAP) 수수료가 **30%로 인상**되면서, 앱에서 판매하는 재화의 수익성이 크게 떨어질 우려가 있었다.
- 인앱결제만 제공하는 한, 매출의 30%가 고정적으로 플랫폼 수수료로 빠져나가는 구조였다.

## 해결

### 1. Saga 패턴 기반 보상 트랜잭션 + Slack 실시간 알림

재화 지급 처리가 실패하면 **이미 승인된 TossPayments 결제를 자동으로 되돌리고**, 그 사실을 실시간으로 알리는 구조를 구현했다.

- **보상 트랜잭션(자동 환불)** — 결제 로그 기록 / 재화 지급 트랜잭션이 실패하면, 직전에 성공한 TossPayments 결제 건을 **취소(환불) API로 롤백**한다. 외부 결제와 내부 재화 지급이 **"둘 다 완료" 또는 "둘 다 없음"** 중 하나로만 수렴하도록 만들어 정합성을 확보했다.
- **결제 실패 로그 적재** — 실패한 결제 건의 요청/응답, 예외 내용, 환불 처리 결과를 별도로 남겨 **원인 파악과 재처리의 근거**로 삼았다.
- **Slack 실시간 알림** — 결제 실패와 자동 환불 결과를 Slack으로 즉시 통지해, **담당자가 대시보드를 보지 않아도 이슈를 인지**하고 고객 대응에 바로 착수할 수 있게 했다. 실패 유형이 쌓이면서 다양한 결제 이슈에 신속 대응할 수 있는 체계가 마련됐다.

### 2. 토스페이먼츠 웹결제 유도 플로우 설계

- iOS 앱에서 재화 구매 시, 인앱결제 대신 **WebView로 토스페이먼츠 웹결제 페이지를 띄우는 결제 플로우**를 설계했다.
- 결제 승인부터 재화 지급까지를 서버가 직접 처리하도록 붙여, 웹결제 경로를 통한 구매가 인앱결제와 동일한 사용자 경험으로 완료되도록 했다.
- 웹결제 비중이 늘수록 **인앱결제 수수료(30%) 부담을 줄이는** 구조를 만들었다.

---

## 결과

- 재화 지급 트랜잭션이 실패해도 **TossPayments 결제가 자동 환불**되어, "결제는 됐는데 재화가 없는" 정합성 깨짐 상태가 자동으로 해소된다. 결제–재화 지급 간 데이터 정합성이 보장된다.
- 결제 실패를 **Slack으로 즉시 인지**하게 되어, 원인 파악과 다양한 결제 이슈에 신속하게 대응할 수 있는 체계를 갖췄다.
- 토스페이먼츠 웹결제 플로우를 통해 인앱결제 대신 **웹결제로 유도**할 수 있게 되었고, 웹결제 비중 증가로 **인앱결제 수수료를 절감**하며 매출 개선에 기여했다.
