> 라이프오아시스에서 운영하는 서비스 **MAUM**의 **근처 친구 추천 기능** 개발 기록입니다. 유저별로 가까운 위치의 친구 50명을 추천해야 하는데, 매 요청마다 800만 유저의 위치정보를 전체 스캔하면 서버 부하가 감당되지 않는 구조였습니다. 이를 **3시간 주기 배치가 근처 친구 목록을 미리 계산해 Redis에 캐싱**하고, 추천 API는 캐싱된 결과만 읽어 응답하는 구조로 바꾼 과정을 정리합니다.

## 프로젝트 개요

- **회사 / 서비스**: 라이프오아시스 / MAUM
- **프로젝트명**: 근처 친구 추천 기능 개발
- **일정**: 2025.03 (1개월)
- **기술 스택**: Redis (Geolocation · Set) · MySQL · Kubernetes (K8s)

**설계 기준**

- 유저별 근처 친구 50명 추천 기능 필요
- 대상 유저 규모 약 800만
- 매 요청마다 전체 유저 위치정보를 조회하는 방식은 쿼리 부하가 크므로, **3시간 주기 배치**로 근처 친구 목록을 사전 계산해 **Redis Set 자료구조에 캐싱**하는 방식 채택

## 아키텍처

![MAUM 근처 친구 추천 아키텍처(2025.03) 다이어그램. 사용자가 API 서버(K8s Pod)에 근처 친구 요청을 보내면 API 서버는 Redis에서 SMEMBERS로 캐싱된 근처 친구 Set(nearby_friends:{userId})만 조회해 50명을 응답한다. 사전 계산은 K8s CronJob(3시간 주기 배치)이 담당하며, ① MySQL 유저 DB에서 다중 조건 필터링(국가 정보 일치·탈퇴 여부 제외·최근 1일 이내 로그인)을 적용해 필터링된 유저 위치정보만 조회하고, ② 그 유저들을 Redis GEOADD로 국가별 Geo 인덱스에 등록한 뒤, ③ 각 유저를 기준으로 Redis GEOSEARCH로 반경 내 근처 유저를 탐색하고, ④ 가까운 순 근처 친구 50명을 산출해 Redis Set(GEO + Set 자료구조)에 저장·캐싱한다. 800만 전체 유저를 매 요청마다 스캔하는 대신 필터링된 대상만 배치에서 GEO 연산하여 서버 부하를 최소화하는 구조다](/assets/img/posts/maum-near-friends/maum_nearby_friend_architecture_v2.drawio.png)

*MAUM 근처 친구 추천 아키텍처 (2025.03) — 사전 계산(K8s CronJob, 3시간 주기: MySQL 다중 조건 필터링 → `GEOADD` → `GEOSEARCH` → 근처 친구 50명을 `nearby_friends:{userId}` Redis Set에 캐싱)과 캐시 조회(API 서버가 `SMEMBERS`로 캐싱된 Set만 읽어 응답) 두 경로로 분리된다.*

전체 흐름은 **사전 계산(3시간 주기 배치) → 캐시 조회(추천 API)** 두 경로로 분리된다.

**1. 사전 계산 — 3시간 주기 배치 (K8s CronJob)**

1. **대상 유저 로드** — MySQL에서 유저 위치정보(위·경도)를 조회하되, 이 단계에서 **다중 조건 필터링**을 적용해 연산 대상을 줄인다.
   - **탈퇴 여부** — 탈퇴한 유저 제외
   - **최근 1일 이내 로그인 여부** — 활성 유저만 대상
   - **국가 정보** — 국가 단위로 그룹핑 (다른 국가의 유저는 애초에 "근처"가 될 수 없으므로 탐색 공간에서 분리)
2. **Geo 인덱스 적재** — 필터링된 유저를 국가별 Redis Geolocation 키에 `GEOADD`로 적재한다. (Redis GEO는 내부적으로 Sorted Set + geohash 스코어로 좌표를 관리한다.)
3. **근처 친구 50명 계산** — 각 유저를 기준점으로 `GEOSEARCH ... BYRADIUS ... ASC COUNT 50` 를 수행해 가까운 순으로 최대 50명을 뽑는다.
4. **유저별 Set 캐싱** — 계산 결과를 `nearby_friends:{userId}` 형태의 **Redis Set**에 저장하고, 다음 배치 주기(3시간)보다 넉넉한 TTL을 건다. 배치가 끝나면 800만(활성 필터 적용 후 그보다 적은) 유저 각각에 대한 추천 목록이 Redis에 준비된다.

**2. 캐시 조회 — 추천 API (K8s Deployment)**

- 유저가 근처 친구 추천을 요청하면 API는 MySQL을 거치지 않고 `nearby_friends:{userId}` **Set 하나만 조회**해 즉시 반환한다.
- 위치 스캔·거리 계산이 요청 경로에서 완전히 빠지므로, 요청량이 늘어도 응답 비용은 Set 조회 비용으로 고정된다.

**K8s 구성**

- 배치는 **CronJob**으로 3시간마다 기동, 추천 API는 **Deployment**로 상시 운영해 배치 부하와 서비스 트래픽을 격리했다.

## 문제

### 요청마다 800만 유저 위치정보를 전체 스캔하는 구조

근처 친구 추천을 요청 시점에 즉석 계산하면, 유저 1명의 요청을 처리하기 위해 **800만 유저의 위치정보를 전부 훑고 거리 계산**을 해야 한다.

- 요청 1건당 O(N)(N = 800만) 스캔이 발생하고, 동시 요청이 늘어나면 O(N × 요청 수)로 부하가 선형 증가한다.
- 위치정보 원천인 MySQL에 매 요청마다 대량 조회가 몰려 DB 부하와 응답 지연이 커진다.
- 탈퇴자·비활성 유저·다른 국가 유저까지 모두 스캔 대상에 포함되어, 실제로는 추천 후보가 될 수 없는 데이터에까지 연산을 낭비한다.

트래픽이 조금만 늘어도 추천 기능이 서비스 전체의 병목이 되는 구조였다.

---

## 해결

### 3시간 주기 배치 사전 캐싱 + 다중 조건 필터링

추천 결과를 **요청 시점이 아니라 배치 시점에 미리 계산**하고, 요청은 캐시만 읽도록 분리했다.

- **사전 캐싱으로 요청 경로에서 스캔 제거** — 3시간 주기 배치가 유저별 근처 친구 50명을 계산해 `nearby_friends:{userId}` Redis Set에 저장한다. 추천 API는 이 Set만 조회하므로, 요청당 비용이 O(N) 스캔에서 **O(1) 캐시 조회**로 떨어지고 요청량과 무관해진다.
- **Redis Geolocation으로 근접 탐색 위임** — 거리 계산을 애플리케이션에서 하지 않고 Redis GEO(`GEOADD` / `GEOSEARCH`)에 맡겼다. geohash 기반 인덱스 덕에 "반경 내 가까운 순 50명" 조회가 전체 스캔 없이 처리된다.
- **다중 조건 필터링으로 연산 대상 최소화** — 배치가 MySQL에서 유저를 읽는 단계에서 **탈퇴 여부 · 최근 1일 이내 로그인 여부 · 국가 정보**로 걸러, Geo 인덱스에 올리는 유저 수 자체를 줄였다. 특히 **국가 단위 분리**로 탐색 공간을 국가별로 쪼개 유효 N을 크게 낮췄다. 추천 후보가 될 수 없는 데이터에 연산을 쓰지 않게 되어 배치의 시간복잡도가 줄었다.
- **배치와 API의 부하 격리 (K8s)** — 무거운 사전 계산은 CronJob으로, 사용자 트래픽을 받는 추천 API는 Deployment로 나눠, 3시간마다의 배치 부하가 서비스 응답에 영향을 주지 않도록 했다.

---

## 결과

- 추천 API가 캐싱된 Redis Set만 조회하게 되어, **요청량이 늘어도 일정한 응답 속도**로 근처 친구 50명을 제공한다. 요청 경로에서 800만 유저 스캔과 MySQL 대량 조회가 사라졌다.
- 위치 기반 근접 탐색을 Redis Geolocation에 위임하고, 다중 조건 필터링으로 연산 대상을 줄여 **3시간 배치가 안정적으로 완주**하는 구조를 확보했다.
- 배치(CronJob)와 추천 API(Deployment)를 분리해, **800만 규모 유저 기반에서도** 사전 계산 부하와 서비스 트래픽이 서로 간섭하지 않는 안정적인 운영 기반을 마련했다.
