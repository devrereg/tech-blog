> 게이트를 통과한 발급을 그 자리에서 데이터베이스에 적는 대신, Kafka에 "발급 요청됨" 한 줄을 던지고 응답을 먼저 돌려준다. 저장은 뒤에서 따라온다. 빨라진 응답, 그리고 "한 번 보낸 메시지가 두 번 도착할 수 있다"는 새 전제. (2026-06-09)

## 무슨 문제를 풀고 있었나

100장 한정 쿠폰에 2,000명이 동시에 몰려도 정확히 100장만 나가게 하는 게 이 시리즈의 한 줄짜리 목표다. 앞선 글에서 재고를 깎고 말고를 판단하는 일을 데이터베이스 밖 Redis로 옮겼다([이전 글 "재고 판단을 Redis로 옮기기"]({% post_url 2026-06-07-coupon-concurrency-5-redis-gate %})). Redis의 빠른 카운터를 일종의 번호표 기계로 쓴 것이다. 들어오는 요청마다 번호표를 한 장씩 원자적으로 뽑게 하고, 100장이 떨어지면 더 안 준다. 통과한 요청만 데이터베이스에 "누가 받아갔다"는 한 줄을 남겼다.

그 구조는 빨랐지만, 한 가지 위험을 그대로 안고 있었다. 발급 처리가 이렇게 한 호출 안에서 순서대로 일어났기 때문이다.

1. Redis 게이트에서 번호표를 받는다(카운터 1 차감).
2. 데이터베이스에 발급 기록을 남긴다.
3. 2가 실패하면 번호표를 반납한다(카운터 1 복구).

문제는 1과 2 사이다. 번호표를 받은 직후, 데이터베이스에 적기도 전에 서버가 죽으면 3을 실행할 코드가 영영 돌지 않는다. 발급도 안 됐는데 재고만 한 장 줄어든 유령 슬롯이 생긴다. 동기 호출 + 그 자리에서 되돌리기라는 구조가 가진 근본적인 틈이었다.

이번 글은 2번(데이터베이스 저장)을 호출에서 떼어내, 통과 사실을 메시지로 남기고 저장은 뒤에서 처리하게 만든다. 이를 위해 쓴 도구가 Kafka다.

## Kafka가 뭔지부터 — 우체통과 집배원

처음 보는 사람을 위해 비유로 풀어본다.

- **토픽(topic)**: 메시지를 쌓아두는 우체통이라고 보면 된다. 우리는 `coupon-issue-requests`라는 우체통을 하나 만들었다.
- **프로듀서(producer)**: 우체통에 편지를 넣는 쪽. 발급 요청을 받은 서버가 "이 사람이 이 쿠폰 발급받기로 했음"이라는 쪽지를 넣는다.
- **컨슈머(consumer)**: 우체통을 비우며 편지를 처리하는 집배원. 쪽지를 하나씩 꺼내 데이터베이스에 발급 기록을 적는다.
- **파티션(partition)**: 우체통 안에 나뉜 칸들. 같은 칸 안에서는 넣은 순서대로 꺼내진다. 우리는 3칸으로 나눴다.

여기서 핵심은 편지를 넣는 일과 처리하는 일이 분리된다는 점이다. 편지를 넣자마자 "접수됐습니다"라고 손님에게 답할 수 있고, 실제 처리(데이터베이스 저장)는 집배원이 나중에 한다. 손님을 기다리게 하지 않는다.

쪽지 자체는 단출하다.

```kotlin
data class CouponIssueRequested(
    val couponId: Long,
    val userId: Long,
)
```

## 바뀐 흐름 — 게이트 통과 → 발행 → (나중에) 저장

발급 요청 하나가 어떻게 흐르는지 새 그림으로 보면 이렇다.

```text
요청 ──▶ ① Redis 게이트(재고+중복 원자 검사)
            │ 통과
            ▼
         ② Kafka 우체통에 "발급 요청됨" 넣기 (acks=all 동기 확인)
            │ 넣었음
            ▼
         "접수됨" 응답 ◀── 여기서 손님은 끝. DB엔 아직 아무것도 없음.

   ··· (시간이 조금 흐른 뒤) ···

   집배원(컨슈머) ──▶ ③ 우체통에서 꺼내 DB에 발급 기록 저장
```

조율을 맡는 서비스는 이렇게 짧다.

```kotlin
fun issue(couponId: Long, userId: Long) {
    when (reservation.reserveWithDedup(couponId, userId)) {
        ReservationResult.OUT_OF_STOCK -> throw OutOfStockException()
        ReservationResult.DUPLICATE -> throw DuplicateIssueException(couponId, userId)
        ReservationResult.RESERVED -> Unit
    }
    try {
        publisher.publish(CouponIssueRequested(couponId, userId))
    } catch (e: Exception) {
        // 게이트는 통과했으나 발행 실패 → 슬롯 반납(보상) 후 재전파.
        try {
            reservation.releaseWithDedup(couponId, userId)
        } catch (releaseError: Exception) {
            e.addSuppressed(releaseError)
        }
        throw e
    }
}
```

데이터베이스 저장 코드가 이 메서드에서 사라진 게 보일 것이다. 저장은 우체통 반대편의 컨슈머가 맡는다.

## 게이트가 한 가지 일을 더 한다 — 중복까지 원자적으로

이전 글의 게이트는 "재고 보고 → 깎기"만 원자적으로 했다. 이번엔 같은 한 덩어리 안에서 1인 1매 중복까지 막는다. 발급받은 사람들의 사용자 ID(userId)를 Redis 집합(SET)에 모아두고, 거기 이미 있으면 거절한다.

```lua
-- KEYS[1] = coupon:stock:{couponId}   (재고 카운터)
-- KEYS[2] = coupon:issued:{couponId}  (발급자 집합)
-- ARGV[1] = userId
local remaining = tonumber(redis.call('GET', KEYS[1]))
if remaining == nil or remaining <= 0 then
  return -1                                    -- 소진
end
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return -2                                    -- 이미 받은 사람
end
redis.call('SADD', KEYS[2], ARGV[1])           -- 발급자로 표시
return redis.call('DECR', KEYS[1])             -- 재고 1 깎고 남은 값 반환
```

세 갈래 결과가 나온다 — 통과(`RESERVED`), 소진(`OUT_OF_STOCK`), 중복(`DUPLICATE`). 중요한 건 소진과 중복은 카운터를 깎지 않고 즉시 거절한다는 점이다. 깎지 않았으니 되돌릴 것도 없다. 보상이 필요한 경우는 오직 "깎았는데 그다음 발행이 실패한" 통과 케이스뿐이다.

소진을 중복보다 먼저 검사하는 데에도 이유가 있다. 재고가 0인데 중복 검사를 먼저 해서 집합에 아이디를 넣어버리면, 발급도 못 받은 사람이 발급자 집합을 오염시킨다. 소진을 먼저 봐서 그런 흔적을 남기지 않는다.

## acks=all — "확실히 들어갔다"를 기다린다

편지를 우체통에 넣는 코드는 동기로 응답을 기다린다.

```kotlin
override fun publish(event: CouponIssueRequested) {
    kafkaTemplate.send(TOPIC, event.couponId.toString(), event)
        .get(SEND_TIMEOUT_SECONDS, TimeUnit.SECONDS)  // 브로커 확인을 동기로 대기
}
```

`acks=all`은 "메시지가 브로커에 안전하게 기록될 때까지 보낸 걸로 치지 않겠다"는 설정이다. 그리고 `.get()`으로 그 확인이 올 때까지 동기로 기다린다. 왜 굳이 기다리느냐면, 발행이 실패했는지를 그 자리에서 알아야 깎아둔 번호표를 반납할 수 있기 때문이다. 비동기로 던지고 돌아서면, 실패를 알았을 땐 이미 보상할 맥락을 잃은 뒤다.

발행 시 메시지 키를 `couponId`로 준 것도 의미가 있다. Kafka는 같은 키를 같은 칸(파티션)에 넣어 그 안에서 순서를 보장한다. 같은 쿠폰의 발급 요청들이 한 칸에 모여 순서대로 처리된다.

## 보상이 두 곳으로 쪼개졌다 — 이번 글에서 가장 중요한 부분

이전 구조에서 "되돌리기"는 한 군데였다 — 저장이 실패하면 같은 호출에서 반납. 이제 저장이 우체통 반대편으로 넘어갔으니, 되돌릴 상황도 두 군데로 나뉜다.

**(1) 동기 보상 — 발행 자체가 실패했을 때.** 게이트는 통과했는데 Kafka에 편지를 못 넣었다면, 요청 스레드가 그 자리에서 슬롯을 반납한다(`releaseWithDedup` = 재고 카운터 INCR + 발급자 집합에서 제거). 위의 `issue` 코드의 `catch` 블록이 그 일이다.

**(2) 비동기 보상 — 집배원이 저장하다 실패했을 때.** 편지는 잘 들어갔는데, 나중에 컨슈머가 데이터베이스에 적다가 실패할 수 있다. 이때는 실패의 종류로 갈린다.

```kotlin
@KafkaListener(topics = ["coupon-issue-requests"], groupId = "coupon-issue-consumer")
fun consume(event: CouponIssueRequested, ack: Acknowledgment) {
    try {
        persist.persist(event.couponId, event.userId)
    } catch (e: DuplicateIssueException) {
        // 멱등 중복(재배달) → 반납하지 않고 폐기
        log.warn("멱등 중복(재배달) 폐기 — couponId={} userId={}", event.couponId, event.userId)
    } catch (e: Exception) {
        // 그 외 영구 실패 → 깎인 슬롯 헛됨 → 반납
        reservation.releaseWithDedup(event.couponId, event.userId)
    } finally {
        ack.acknowledge()
    }
}
```

이 분기를 이해하려면 Kafka의 한 가지 성질을 먼저 알아야 한다.

## at-least-once — "최소 한 번"은 "두 번"일 수도 있다

Kafka는 기본적으로 at-least-once(최소 한 번) 전달을 한다. 즉 메시지가 적어도 한 번은 처리되도록 보장하지만, 그 대가로 같은 메시지가 두 번 처리될 수도 있다. 집배원이 편지를 처리하고 "다 처리했다"고 우체통에 보고하기 직전에 죽으면, 우체통은 그 편지를 아직 안 처리된 걸로 알고 다음 집배원에게 다시 건넨다. 같은 쪽지가 두 번 배달되는 것이다.

그래서 컨슈머는 같은 쪽지를 두 번 받아도 탈이 안 나야 한다. 이걸 멱등성(idempotency)이라고 한다. 우리는 발급 기록에 "한 쿠폰당 한 사용자 한 번"이라는 데이터베이스 유니크 제약을 걸어 이를 보장한다. 같은 쪽지가 두 번째로 오면, 첫 번째에서 이미 적힌 행 때문에 유니크 위반이 나고 — 그게 위 코드의 `DuplicateIssueException`이다.

여기서 분기의 핵심 판단이 나온다.

- **유니크 위반 = 재배달이다.** 진짜 중복 요청(같은 사람이 두 번 발급)은 이미 게이트의 Redis 집합이 막아 우체통까지 오지도 못한다. 그러니 컨슈머에서 유니크 위반이 보이면, 그건 "정상 발급 한 건이 두 번 배달된" 경우다. 첫 번째 행이 그 슬롯을 정당하게 갖고 있으므로 반납하면 안 된다. 반납하면 슬롯이 하나 더 풀려 101장이 나갈 수 있다. 그래서 조용히 폐기만 한다.
- **그 외 영구 실패 = 슬롯이 헛됐다.** 예를 들어 그 사용자가 존재하지 않으면 발급 행을 만들 수 없다. 이미 깎인 번호표는 영영 쓸 데가 없으니 반납한다.

같은 "저장 실패"라도 한쪽은 반납하면 안 되고, 한쪽은 반납해야 한다. 이 구분이 이번 구조에서 가장 미묘한 지점이다.

## 결과 — 같은 100장, 응답은 빠르지만 일관성은 "나중에"

시리즈 내내 쓴 같은 시험이다: 재고 100, 서로 다른 사용자 2,000명이 동시에 발급. 다만 이번엔 응답을 받았다고 데이터베이스에 행이 있는 게 아니다. 발행이 끝나도(= 접수 응답을 받아도) 저장은 뒤따라온다. 그래서 테스트는 컨슈머가 우체통을 다 비울 때까지(드레인) 기다린 뒤에야 데이터베이스 발급 행 수를 센다. 이게 결과적 일관성(eventual consistency)이다 — 지금 당장은 어긋나 보여도, 잠시 뒤엔 맞아떨어진다.

남긴 로그는 이랬다.

```text
Redis+Kafka 동시성 결과 — 게이트통과(접수)=100 거절=1900 Redis잔여=0 발급행=100 접수까지=194ms
Redis+Kafka 드레인 완료까지=414ms
```

불변식은 그대로 지켜졌다 — 통과 100, 거절 1,900, Redis 잔여 0, 드레인 후 발급 행 정확히 100. 다른 방법들과 나란히 놓으면 이렇다.

| 방법 | 줄 서기 | 재시도 | 대략 소요 |
| --- | --- | --- | --- |
| 비관 락 | 있음 | 없음 | — |
| 낙관 락 | 없음 | 많음 (100건당 58~121회) | 약 430~690ms |
| Redis 게이트(동기 저장) | 없음 | 없음 | 약 153ms |
| Redis 게이트 + Kafka 비동기 | 없음 | 없음 | 접수 ≈194ms / 드레인 ≈414ms |

읽는 법이 좀 다르다. 이 방법엔 시점이 둘이다.

- **접수까지(≈194ms)**: 손님이 "접수됨"을 받기까지. 동기 저장 방법(≈153ms)과 비슷한 수준이다. 손님 입장에서 체감 응답은 빠르다.
- **드레인 완료까지(≈414ms)**: 100건이 실제로 데이터베이스에 다 박히기까지. 이건 뒤로 밀린다.

비동기의 본질이 이 숫자에 그대로 드러난다. 응답을 빨리 돌려주는 대신, "발급이 진짜 데이터베이스에 남는" 시점은 나중으로 미룬다. 일관성을 즉시가 아니라 "결국"에 맞춘다.

## 구현의 한계 / 문제점

Kafka는 앞 글이 남긴 "저장 중 서버가 죽으면?" 문제를 상당 부분 닫았다. 편지가 브로커에 안전히 기록되니(acks=all), 집배원이 처리하다 죽어도 다음 집배원이 다시 처리한다. 하지만 솔직히 다 푼 건 아니다.

1. **게이트 통과와 발행 사이의 틈은 여전히 남는다.** 이번에 닫은 건 "발행 이후" 구간이다. 그런데 Redis 카운터를 깎은 직후, Kafka에 편지를 넣기 전에 서버가 죽으면? 여전히 보상할 코드가 안 돈다 — 깎인 슬롯이 편지도 못 남기고 증발한다. 틈을 더 줄였을 뿐 없애진 못했다. 이걸 완전히 닫으려면 "깎는 것과 기록하는 것"을 한 동작으로 묶어야 하는데(Redis Stream이나 트랜잭셔널 아웃박스 같은 기법), 이번 범위 밖이다.

2. **일시적 장애와 영구 장애를 구분하지 않는다.** 컨슈머는 유니크 위반이 아닌 모든 실패를 "영구 실패"로 보고 반납 후 폐기한다. 하지만 데이터베이스가 잠깐 끊긴 것뿐이라면? 곧 회복될 텐데도 정당한 당첨자가 슬롯을 잃고 조용히 탈락한다. 실제 시스템은 잠깐의 실패는 잠시 뒤 다시 시도(재시도/백오프)하고, 끝내 안 되는 것만 따로 빼두는 곳(DLQ, Dead Letter Queue)으로 보낸다. 이 구분은 일부러 미뤄뒀다.

3. **"유니크 위반 = 재배달"은 Redis 집합을 믿는다는 전제 위에 있다.** 컨슈머가 반납을 건너뛰는 판단은 "진짜 중복은 게이트의 발급자 집합이 이미 막았다"를 믿기에 성립한다. 만약 그 집합이 멤버를 조용히 잃을 수 있다면(예: 만료·정리 정책이 잘못 걸리면) 이 가정이 깨진다. 그땐 메시지마다 고유한 처리 식별자를 따로 둬서 멱등성을 보장해야 한다.

4. **아직 실제로 쓸 준비는 아니다.** 내부 로직과 테스트까지만 있다. 발급 시작 전 카운터에 재고를 채우는 일을 테스트에서는 직접 해주지만, 발급 시작·종료에 맞춰 자동으로 채우는 흐름도, 이 경로를 바깥에 노출하는 REST 엔드포인트도 아직 없다.

## 다음에 해볼 내용

이번 글은 발급 처리를 비동기로 떼어내 응답을 빠르게 돌려주고, "같은 메시지가 두 번 와도 안전하다"는 멱등성을 데이터베이스 유니크 제약으로 세웠다. 그래도 앞 글에서 떠안은 숙제 하나는 그대로다 — 재고의 권위는 Redis에 있고 데이터베이스의 재고 숫자는 더 이상 진실을 말하지 않는다는 어긋남. 다음 글에서는 이 어긋남을 다룬다.

- Redis 카운터와 데이터베이스 발급 기록을 주기적으로 대조해 차이를 메우는 재동기화.
- 그리고 이 경로를 실제로 쓰기 위한 재고 시딩 흐름과 REST 연결.

잣대는 그대로 둔다 — 재고 100에 서로 다른 2,000명이 동시에 발급하는 그 시험으로 똑같이 재서 견준다.
