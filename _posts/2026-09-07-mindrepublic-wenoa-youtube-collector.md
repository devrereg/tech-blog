> 마인드리퍼블릭에서 운영하는 서비스 **WENOA**의 **유튜브 콘텐츠 실시간 수집 파이프라인** 개발 기록입니다. 모니터링 대상 유튜브 채널에서 새 콘텐츠가 발행되면 이를 실시간으로 수집해 내부 DB에 적재하는 구조로, 수집량이 일 20만 건 이상으로 급증하면서 마주친 **SQS 메시지 적체 · MySQL 커넥션 초과 · YouTube API 일일 호출 한도(credit) 소진** 세 가지 문제를 다룹니다.

## 프로젝트 개요

- **회사 / 서비스**: 마인드리퍼블릭 / WENOA
- **프로젝트명**: 유튜브 콘텐츠 실시간 수집
- **일정**: 2025.10 (1개월)
- **기술 스택**: AWS (EC2 `t3a.medium`, SQS, DLQ, CloudWatch, AutoScaling) · FastAPI · MySQL (`t4g.medium`) · YouTube Data API v3

**설계 기준**

- 피크 TPS: 10 call/sec
- EC2(`t3a.medium`) 1~3대 AutoScaling을 기준으로 인프라 설계
- 수집 지연 없이 발행 콘텐츠를 실시간에 가깝게 적재

## 아키텍처

![WENOA 유튜브 콘텐츠 실시간 수집 파이프라인 아키텍처(2025.10) 다이어그램. 모니터링 대상 유튜브 채널에서 새 콘텐츠가 발행되면 수집 트리거가 Producer를 통해 AWS SQS 큐에 수집 메시지를 적재한다. Consumer는 EC2 t3a.medium 1~3대(FastAPI, AutoScaling)로 구성되며 SQS 큐를 병렬로 폴링해 메시지를 처리하고, 처리에 반복 실패한 메시지는 DLQ(Dead Letter Queue)로 이동한다. Consumer는 YouTube Data API v3를 호출해 콘텐츠 메타데이터를 조회하는데, 콜백으로 받은 1차 데이터를 먼저 MySQL(t4g.medium)에 저장하고 50개가 쌓이면 콘텐츠 ID 50개를 한 번에 묶어 일괄 호출(1 credit)로 2차 업데이트한다. CloudWatch는 SQS 큐의 대기 메시지 수를 모니터링해 100개 이상 적재되면 AutoScaling으로 EC2를 최대 3대까지 증설하고, 각 서버의 로그와 메트릭을 수집한다](/assets/img/posts/mindrepublic-wenoa-youtube-collector/wenoa_youtube_collection_architecture.drawio.png)

*WENOA 유튜브 콘텐츠 실시간 수집 파이프라인 (2025.10) — 발행 감지 → SQS 적재 → EC2 컨슈머(FastAPI, AutoScaling 1~3대) 병렬 처리 → MySQL 1차 저장 후 50건 단위 배치로 YouTube Data API 2차 업데이트. 실패 메시지는 DLQ로 격리하고, 큐 적체는 CloudWatch가 감지해 EC2를 증설한다.*

전체 흐름은 **발행 감지 → 큐 적재 → 병렬 소비 → 배치 보강**의 4단계로 나뉜다.

1. **발행 감지 & 큐 적재** — 모니터링 대상 채널에서 새 콘텐츠가 확인되면 Producer가 수집 메시지를 SQS 큐에 넣는다.
2. **병렬 소비** — EC2(`t3a.medium`) 위의 FastAPI 컨슈머가 큐를 병렬로 폴링해 메시지를 처리한다. 반복 실패 메시지는 DLQ로 격리한다.
3. **1차 저장** — YouTube Data API 콜백으로 받은 기본 데이터를 즉시 MySQL에 적재한다.
4. **2차 배치 보강** — 1차 저장분이 50건 쌓이면 콘텐츠 ID 50개를 묶어 한 번의 API 호출로 상세 정보를 받아 일괄 업데이트한다.

## 문제

### ① SQS 메시지 적체

유튜브 채널에서 발행되는 콘텐츠가 **일 20만 건 이상으로 증가**하면서, 컨슈머의 처리 속도가 유입 속도를 따라가지 못해 **SQS 큐에 메시지가 적체**되기 시작했다. 큐에 쌓인 만큼 콘텐츠 수집이 지연됐다.

### ② MySQL DB 커넥션 초과

수집 트래픽이 늘면서 **MySQL DB 커넥션 수가 한계치에 도달**했다. 커넥션을 확보하지 못한 요청이 실패했다.

### ③ YouTube API 일일 호출 한도(credit) 소진

YouTube Data API는 호출할 때마다 요청 비용을 **credit**으로 차감하고, **하루에 쓸 수 있는 총량이 10,000 credit**으로 고정돼 있다(자정 초기화). 콘텐츠를 **1건씩 개별 조회하면 1건당 1 credit**이 나가므로, 하루에 수집할 수 있는 데이터량이 최대 1만 건 수준으로 묶여 한계가 명확했다. credit을 다 쓰면 그날 남은 호출은 전부 거부된다.

## 해결

### ① 컨슈머 병렬도 상향 + 큐 길이 기반 오토스케일링

- 컨슈머 서버의 **병렬 처리 개수를 늘려** 서버당 동시 처리량을 높였다.
- SQS에 **메시지 100개 이상 적재되면 EC2가 자동 증설**되도록 CloudWatch 지표 기반 AutoScaling(1~3대)을 구성했다. 유입이 몰리면 컨슈머 대수가 늘어 처리량이 따라 올라가고, 적체가 해소되면 다시 축소된다.

### ② MySQL 최대 커넥션 수 조정

- DB 세션에 무리가 가지 않는 범위를 확인한 뒤, **최대 커넥션 수를 80개 → 200개로 상향**했다. 늘어난 컨슈머·병렬 처리량이 필요로 하는 커넥션을 확보할 수 있게 됐다.

### ③ 50건 단위 배치 호출로 credit 절약

- YouTube Data API는 **콘텐츠 ID를 50개까지 묶어 한 번에 요청해도 1 credit만 차감**된다(1건씩 50번 = 50 credit → 50건 묶음 = 1 credit). 이 점을 활용해 조회 방식을 2단계로 나눴다.
  - **1차** — 콜백으로 받은 데이터를 먼저 저장한다.
  - **2차** — 1차 저장분이 **50개 쌓이면 콘텐츠 ID 50개를 묶어 한 번에 호출**하고, 받은 상세 정보로 일괄 업데이트한다.
- 건별 호출 대비 credit 소모를 1/50로 낮췄다.

## 결과

- **SQS 적체 해소** — 병렬도 상향과 큐 길이 기반 EC2 증설로, 일 20만 건 이상 유입에도 콘텐츠 수집 지연 없이 안정적으로 처리한다.
- **커넥션 부족 요청 실패 제거** — 최대 커넥션 80 → 200 조정으로 커넥션 고갈로 인한 요청 실패 없이 서비스가 안정적으로 운영된다.
- **API 사용 효율 극대화** — 50건 배치 처리로 동일한 하루 10,000 credit 안에서 **하루 최대 50만 건**(10,000 credit × 50건)의 콘텐츠 데이터를 확보할 수 있게 됐다.
