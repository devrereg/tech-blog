## 프로젝트 개요

- **회사 / 서비스**: 마인드리퍼블릭 / WENOA
- **프로젝트명**: 유튜브 콘텐츠 실시간 수집 파이프라인 성능 개선
- **일정**: 2025.10 (1개월)
- **역할**: 수집 파이프라인 설계 · 컨슈머 개발 · 인프라 및 DB 튜닝
- **기술 스택**
  - Backend: FastAPI (Python) · YouTube Data API v3
  - Infra: AWS (EC2, SQS, DLQ, CloudWatch, AutoScaling) · MySQL


---

## 문제

모니터링 대상 유튜브 채널의 신규 콘텐츠가 **일 20만 건 이상**으로 늘어나면서 세 가지 한계가 동시에 드러났다.

- **SQS 메시지 적체**: 컨슈머 처리 속도가 유입 속도를 따라가지 못해 큐에 메시지가 쌓이고, 그만큼 수집이 지연됐다.
- **MySQL 커넥션 초과**: 수집 트래픽 증가로 DB 커넥션이 한계에 도달해 요청이 실패했다.
- **YouTube API credit 소진**: 하루 10,000 credit 한도에서 1건 조회당 1 credit이 차감되어, 하루 수집량이 최대 1만 건으로 묶였다.

---


## 해결

컨슈머 처리량을 **큐 적체량에 맞춰 AutoScaling**하고, 수집 방식을 **즉시 저장 + 50건 배치 보강**의 2단계로 바꿔 처리량과 API 효율을 함께 확보함.


**설계 기준**

- 발행된 콘텐츠를 지연 없이 실시간에 가깝게 적재해야 함
- 유입량 변동에 맞춰 처리량이 자동으로 조절되어야 함
- 한 메시지의 반복 실패가 전체 처리를 막지 않아야 함
- 고정된 API 일일 한도 안에서 수집량을 최대화해야 함


## 아키텍처

![WENOA 유튜브 콘텐츠 실시간 수집 파이프라인 아키텍처(2025.10) 다이어그램](/assets/img/posts/mindrepublic-wenoa-youtube-collector/wenoa_youtube_collection_architecture.drawio.png)


- **발행 감지 & 큐 적재**: 신규 콘텐츠가 확인되면 Producer가 수집 메시지를 SQS에 적재
- **병렬 소비**: EC2 위 FastAPI 컨슈머의 병렬 처리 수를 늘리고, SQS 대기 메시지 100개 이상 시 EC2를 최대 3대까지 자동 증설
- **실패 격리**: 반복 실패한 메시지는 DLQ로 분리
- **DB 커넥션 조정**: 늘어난 컨슈머와 병렬 처리량에 맞춰 MySQL 최대 커넥션을 80 → 200으로 상향
- **2단계 수집**: 콜백으로 받은 1차 데이터를 즉시 저장하고, 50건이 쌓이면 콘텐츠 50개를 묶어 한 번의 API 호출(1 credit)로 상세 정보를 일괄 업데이트


**2단계 수집 구조를 선택한 이유**: YouTube Data API는 콘텐츠 1건을 조회하든 50건을 묶어 조회하든 동일하게 1 credit이 차감된다. 건별 조회는 실시간성은 좋지만 credit 소모가 크기 때문에, 기본 데이터는 즉시 저장해 실시간성을 유지하고 상세 정보만 50건씩 배치로 처리했다. 약간의 지연이 있지만 credit 효율을 50배 높였다.

---

## 결과

- 일 20만 건 이상 유입에도 **SQS 적체 없이** 수집 처리
- 커넥션 고갈로 인한 **요청 실패 제거**
- API credit 소모 **1/50 절감**, 동일 한도에서 일 최대 수집량 1만 건 → **50만 건**

---

## 회고
- 최대 커넥션 상향은 빠른 해결책이었지만, 유튜브 채널 수가 증가함에 따라 콘텐츠 발행량이 늘면 컨슈머도 늘어나야 한다. 커넥션 풀 크기 산정이나 RDS Proxy 같은 커넥션 관리 계층을 두었다면 더 근본적인 해결이 되었을 것 같다.
